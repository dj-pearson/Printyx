## Critical Patterns

### Multi-Tenant Isolation (SECURITY CRITICAL)

- 4-tier hierarchy: Platform → Company → Regional → Location
- 8-level roles: Platform Admin (8) → Guest (1)
- Tenant resolution: `x-tenant-id` header → JWT `app_metadata.tenantId` → Session
- **Every query MUST filter by `tenantId`** — missing filters are security vulnerabilities.

```typescript
// CORRECT
await db.query.customers.findMany({ where: eq(customers.tenantId, tenantId) });

// WRONG — leaks across tenants
await db.query.customers.findMany();
```

### Authentication Middleware

**Never define `requireAuth` locally.** Import from centralized locations.

| Middleware            | Import From                             | Use Case                                  |
| --------------------- | --------------------------------------- | ----------------------------------------- |
| `requireAuth`         | `./replitAuth` or `./auth-setup`        | Standard (JWT + session fallback)         |
| `requireSupabaseAuth` | `./middleware/supabase-auth`            | Strict JWT only                           |
| `protectedRoute`      | `./middleware/supabase-auth`            | JWT + Auth + Tenant context (recommended) |
| `platformAdminRoute`  | `./middleware/supabase-auth`            | Platform admin only                       |
| `requirePermission`   | `./middleware/enhanced-rbac-middleware` | RBAC checks                               |

```typescript
import { requireAuth } from '../replitAuth';
import { getUserId, getTenantId } from '../utils/auth-helpers';

app.get('/api/resource', requireAuth, async (req, res) => {
  const tenantId = getTenantId(req);
  const data = await db.query.table.findMany({ where: eq(table.tenantId, tenantId) });
});
```

**Auth helpers** (`utils/auth-helpers`): `getUserId`, `getTenantId`, `isAuthenticated`, `isPlatformAdmin`.

### Unified Business Records

Leads and customers share `business_records`. Status field determines state. Lead-to-customer conversion = status update (preserves history).

TWO TABLES HOLDING ONE CONCEPT IS A COUNTING PROBLEM BEFORE IT IS A MIGRATION (COP-B00). `business_records` was declared canonical and nothing carried it out, and the story sat filed as a dev/prod disagreement until somebody counted: **53 edge functions read `business_records`; 7 touch `companies`, and three of those WRITE it** (`business-records`, `companies`, `import`). `business-records` is the function behind the production CRM account list and its own header calls itself "a backwards-compatible wrapper that delegates to the companies table", so an account created there lands where the opportunity radar, churn risk, QBR, contracts, invoices, service, search and the forecast never look. Count the readers and the writers before believing a story's framing - `grep -rln "\.from('<table>')" supabase/functions/ | sed 's|.*functions/||;s|/.*||' | sort -u` took seconds and changed what the story was. `npm run crm:reconcile` (COP-B00) is the tooling, and its design is the reusable part: it SEPARATES "does this row already exist over there" from "what would it look like there", and answers the first with EXACT keys only. An id match is proof; a `customer_number` match is proof because the column is UNIQUE on both; a NAME match is a CANDIDATE that is reported and SKIPPED, because COP-B10 and COP-B09 both record what it costs to let a migration decide unreviewed that two spellings are one thing - here it fuses two customer accounts. THE ID IS PRESERVED: `deals`, `proposals` and `quotes` all carry an account id, so copying under a fresh uuid orphans every reference the moment the readers switch, and keeping it makes the copy idempotent for nothing. NOTHING IS INVENTED TO SATISFY A NOT NULL - a row with no `created_by` is refused and counted rather than given a sentinel owner, and `source` is written as 'migrated' because the column's 'website' default would claim the account arrived through the web form. A free-text column mapped into a vocabulary (`companies.activity` -> `business_records.status`) COERCES BY RECORD TYPE and COUNTS the coercions in the report; the lead and customer vocabularies do not overlap, so 'qualified' on a customer row is a lead status on the wrong row. Runbook and what still needs the deployed database: `docs/COP-B00-crm-table-reconciliation.md`.

## Database

### Migration Workflow

1. Edit schema in `shared/`
2. `npm run db:generate` → creates SQL in `drizzle/migrations/`
3. Review the SQL
4. `npm run db:migrate` (acquires `__migration_lock`, auto-expires after 5min)
5. Commit schema + migration file together

**Journal integrity (SUPA-005):** drizzle's migrator only applies migrations listed in `drizzle/migrations/meta/_journal.json`. A `*.sql` file with no journal entry is silently NEVER applied → schema drift. `npm run check:migrations` (CI guard) fails when any migration file is unjournaled, two files share a 4-digit prefix, or journal `idx` is non-contiguous. Always add migrations via `db:generate` (which updates the journal) — never hand-drop a `.sql` into `drizzle/migrations/`.

**Snapshot integrity (COP-M00):** drizzle-kit diffs your schema against the snapshot of the LAST journal entry only. That snapshot went missing and `db:generate` silently re-emitted 445 statements of already-applied drift, numbered into a filename collision, so no schema change could ship. Fixed by capturing the drift as a real migration (`0057_cop_m00_schema_reconciliation.sql`, fully idempotent, 118 tables + 15 columns + 9 FKs) rather than absorbing it into a snapshot, which would have left 107 tables permanently un-migrated. `npm run db:generate` is now `scripts/db-generate.mjs`, which renumbers whatever drizzle-kit writes to (highest on-disk prefix + 1) and rewrites the journal tag — drizzle-kit names files from journal LENGTH, and the non-contiguous on-disk numbering is load-bearing (SUPA-002 sequenced `when` values so orphans sort after everything applied). `check:migrations` now HARD-fails when the last entry has no snapshot; the 25 mid-chain gaps stay a warned ratchet. `0057` is committed but UNAPPLIED anywhere — runbook in `docs/COP-M00-migration-tooling.md`. That doc also records the separate finding that `npm run db:migrate` cannot build a fresh database at all: it fails in migration `0000` on uuid-vs-varchar FK key columns and, being one transaction, creates nothing (PA-032).

A tenant_id COLUMN HAS TO BE ABLE TO HOLD A TENANT ID (AUDIT-032). `tenants.id` is `varchar PRIMARY KEY DEFAULT gen_random_uuid()`; 21 tables across four schema files declared `tenant_id integer NOT NULL`, so a read filtered on a real tenant gave **22P02** and an insert gave **42804** - both reproduced on Postgres 16, not inferred. Nothing caught it: tsc cannot, because the column type and the `tenantId` variable agree inside each file and the Express layer types `tenantId` as `any`; `check:phantom-cols` checks column NAMES, not types; and PostgREST leaves `.data` null on error while this code writes `?? []` around it, so the symptom was an EMPTY DASHBOARD, indistinguishable from a table nobody has filled in. That is why six of them - `client_collected_metrics`, `contract_renewal_tracking`, `renewal_analytics`, `supply_monitoring`, `supply_replenishment_analytics`, `supply_usage_history` - sat in `docs/unwritten-tables-baseline.json` as tables nothing writes to, when the truth is that nothing COULD. The affected features are auto-supply replenishment, contract renewal (including the routed `/contract-renewal-autopilot`), document automation and the printyx-client agent. Migration `0062_round_sway.sql` converts all 21 and was PROVEN by applying it to a real Postgres twice, including against a database that had already run the hand-run `_inbound_webhook_events.sql` (which drizzle-kit correctly folded in, since an unjournaled file is invisible to the snapshot - it is `IF NOT EXISTS` for that reason). `npm run check:tenant-id-types` gates both sides at zero, because either alone is wrong here: it reads the Drizzle declarations AND replays the migration chain in journal order, since `0000` creates these columns as integer and `0062` converts them. The workaround the bad type forced is the thing to recognise elsewhere: `predictive-service-dispatch-service.ts` did `eq(clientCollectedMetrics.tenantId, parseInt(tenantId))` to satisfy tsc, and `parseInt` of a uuid is its leading digits (`'550e8400-...'` -> 550) or NaN, so it filtered on a tenant that does not exist. When a tenant id needs coercing, the column is wrong, not the id.

**A scratch Postgres is available, and several "blocked on DB access" stories are not (COP-M07):** this container ships PostgreSQL 16 at `/usr/lib/postgresql/16/bin`. `initdb` refuses to run as root, so run it as the `postgres` user (`su postgres -c "... initdb -D <dir> -U postgres --auth=trust"`), start it on a spare port, apply the migrations statement-tolerantly (`psql -v ON_ERROR_STOP=0 -f` in journal order — `db:migrate` itself dies in `0000`, see above), then insert one `tenants` + `users` row and run `DEMO_USER=<email> npm run seed:demo`. That is enough to verify anything that needs real rows. Two traps it exposes: the demo seeder short-circuits with "Demo data already exists" for a tenant that has any, and `generateId()` produces TENANT-INDEPENDENT ids (`stage-demo-001`) under `onConflictDoNothing`, so seeding a SECOND tenant into the same database reports success and writes NOTHING. Use a fresh database per tenant you want to seed.

**Pipeline stages (COP-M07):** `deals.stage_id` holds a LEGACY `deal_stages.id`; `pipeline_stages.legacy_stage_id` is the bridge CRMX-005 established. `npm run check:stage-resolution` (needs `DATABASE_URL`) asserts every deal resolves to exactly one canonical stage and exits **2** when it cannot connect, so "did not run" is never read as "passed" — run it before and after touching any stage writer. Three defects this closed, each reproduced against a real database: `pipeline_templates.pipeline_type` is NOT NULL and the lazy bootstrap in `supabase/functions/pipeline-config/index.ts` omitted it, so that bootstrap could NEVER succeed and any tenant without a template had a permanently empty board; the explicit template create wrote `stage_type` and `allowed_transitions`, neither of which is a column on `pipeline_stages`, so every create returned "Template saved but stage insert failed" and orphaned the template; and the read paths returned raw rows, so the Stage Type select always showed its placeholder. `stageType` now maps to `is_final_stage`/`is_closed_won`/`is_closed_lost`/`is_active` through `supabase/functions/_shared/pipeline-stage-type.ts`. `allowed_transitions` was dropped rather than given a column — nothing reads it.

`db:push` is dev-only. For an existing DB without migrations: generate baseline, then `npm run db:migrate:baseline` (marks applied without executing).

### Edge path normalization (prod-only 404s) — READ BEFORE TOUCHING ANY EDGE FN

An edge handler NEVER sees its own name in the path. The Coolify dispatcher
(`supabase/functions/server.ts`) resolves the function from URL segment 0 and then
**strips it** (`stripSegments = 1`; it rewrites to `'/' + pathParts.slice(1).join('/')`)
before invoking the handler. So `functions.printyx.net/seo/settings` arrives as
`/settings`.

Therefore **`const resource = url.pathname.split('/').filter(Boolean)[1]` is a bug.**
It reads `undefined`, every `resource === '...'` guard is false, and the function 404s
on EVERY route. Always use the idempotent helper instead — it strips an OPTIONAL
leading prefix, so routing is identical whether the segment is present or already gone:

```typescript
import { normalizePath } from '../_shared/path.ts';
const { parts } = normalizePath(url.pathname, 'seo'); // parts[0] = resource
```

**This is invisible in dev.** If the prefix is not in `crmProxies`, Express serves it
locally and the edge function is never exercised — the outage is prod-only. ALL 169 edge functions are now migrated (2026-07-17); `npm run check:edge-paths` enforces it at 0. seo and deal-desk were each 404ing on EVERY endpoint before that sweep. The impact claim is statically derived — the mechanism is proven but nothing was executed against a deploy, so confirm with one curl per prefix before treating it as an incident writeup.

GPT-5 endpoints (AI-001): `/api/ai/gpt5/*` is served by `supabase/functions/ai-gpt5/` — a `server.ts` alias (`functionName === 'ai' && subPath[0] === 'gpt5'`) plus a `crmProxies` entry `'/api/ai/gpt5': { fn: 'ai-gpt5', pathPrefix: '/gpt5' }`. Only that sub-path is proxied; the rest of `/api/ai` stays on Express and has no frontend caller. Prompt text, model configs and the response parser are duplicated in `_shared/gpt5-prompts.ts` (+ `_shared/crisis-response.ts`) and locked to `server/services/gpt5-service.ts` by `server/tests/unit/gpt5-prompts-parity.test.ts`. A LINK THAT WORKS ON THE MACHINE THAT COMPOSED IT IS NOT A LINK (COP-B14). `BookingPages.tsx` builds its copy button from `${window.location.origin}/book/${slug}` and is right to: the rep reads it on screen and pastes it straight away. PRIVATE RANGES COUNT AS LOCAL (192.168 is reachable from the next desk and from nowhere a prospect will ever be), and the octet tests are exact rather than prefix-ish: 172.32 is outside 172.16-31 and 1.10.x is not 10.x, both of which a lazier regex refuses in the direction of breaking a real deployment. A page with a blank slug returns null rather than a link to `/book/`, and `BookingLinkPicker` lists only `is_active` pages, so nothing on this path can put a 404 in an email; a tenant with no page gets a sentence and a create button rather than an empty list that reads as a failed load. Whenever a URL you build in the client will be STORED and read by someone else later, the origin is a decision, not a convenience.

A COUNT MUST BE SCOPED THE WAY THE LIST BESIDE IT IS SCOPED (CRM-008 AC6). A CARD IN A CATALOGUE IS NOT A CARD ON A SCREEN (COP-B01 AC6). `team-pipeline` and `team-activity` sat in `shared/my-day-layout.ts` from the day the My Day workspace shipped - declared, role-gated at MANAGER, orderable in the customizer, filtered correctly by role level - and rendered NOTHING, because no endpoint answered them and `TodayDashboard`'s `cardSlots` had no entry for either id. `MyDayCardBoundary` showed an empty card rather than an error, so the feature was absent in the politest possible way: a manager could add the card, see a blank, and read it as a quiet week. **The check is mechanical and worth running on any registry-driven UI: every id in the catalogue must have a slot, and `server/tests/unit/team-rollup.test.ts` now asserts exactly that for the team cards.** This is COP-M01's "a configured field the record does not carry" one level up - a configurable surface fails silently in both directions, and only the catalogue-versus-slots comparison sees it.

THE TEAM IS `resolveScope`'s ANSWER, AND A CALLER WITH NO TEAM GETS 403, NOT A ROLL-UP OF THEMSELVES (COP-B01 AC6). `GET /crm/team-rollup` never takes a user list from the client. A scope that resolves to 'own' is refused with INSUFFICIENT_SCOPE, because a one-row team card is not a smaller version of the feature - it is a rep reading a manager surface - and the card treats that 403 as "not a manager any more", rendering nothing with `retry: false` so a demoted user does not re-ask on every focus. `shared/team-rollup.ts` does the grouping PostgREST cannot, and its rules are the ones this repo keeps re-learning: an EXPLICIT UNASSIGNED bucket that the card SHOWS (COP-B10 - a per-rep list that hides ownerless rows stops adding up to the total printed above it); a member with nothing appearing AT ZERO, which is the inverse of NULL-IS-NOT-ZERO and the difference is whether the row was looked for; a total over an uncosted row declared a FLOOR (COP-B05); and an activity with no type counted under `unspecified` rather than discarded. Each half is computed independently and a failure answers **null**, so the card renders nothing - "0 activities this week" about a team that is working is worse than an empty space, and the server already knows which it is.

A `?mine=true` FILTER IS NOT AN ACCESS CHECK, AND THE ITEM ROUTE IS THE WORSE HALF (COP-B04 AC4). `GET /opportunity-radar` filtered on tenant, status and - only when the caller asked - `?mine=true`. Dropping one query parameter returned up to 500 plays across the whole tenant, each naming an account, its machines, the trigger and an estimated dollar value, so every rep could read every other rep's book. No guard saw it: the function IS gated at MANAGER on the two branches that change tenant-wide settings, and its read is open on purpose because a rep has plays - what was missing is that a rep has only SOME plays. The fix is COP-I06's, which is ORDER rather than refusal: `resolveScope` first, `applyUserScope(query, 'owner_id', scope)` on the query BEFORE `mine` and `playType`, so a parameter can only narrow what the tier already allows, with `scopeTier` reported so a shorter list is explicable. **AND THE SAME SCOPE MUST REACH THE ITEM ROUTE**: `POST /:id/dismiss` and `POST /:id/convert` loaded the play by id and tenant alone, and dismissing another rep's play takes it off their board while converting one creates a deal in their name. A uuid is not the control - SEC-TENANT-005 already records that ids travel in URLs, exports and support tickets. Scoping a list and leaving its items open is a half-measure; grep for a handler that filters a list on a caller-supplied `mine`/`ownerId`/`userId` and then serves `/:id` on tenant alone. An UNOWNED row stays actionable for anyone who can see it, which is what `applyUserScope`'s own default already encodes.

`check:phantom-cols` CANNOT SEE A PAYLOAD BUILT BY A HELPER, SO CHECK IT AGAINST `getTableConfig` INSTEAD (COP-B04 AC3). That guard's documented blind spot is a payload assembled as a named variable, and CLAUDE.md cites the deals insert as the example - `dealFromPlay` in `_shared/opportunity-radar.ts` is precisely that shape, so the one-click convert was unverified by anything. `server/tests/unit/radar-list-scope.test.ts` resolves drizzle's `getTableConfig` and asserts two properties over the mapper's emitted keys: every key is a real column, and every NOT NULL column with no default is supplied. That is worth copying wherever an edge function inserts through a helper rather than an inline literal, and it is cheap - the table config is already imported by half a dozen tests here. The same test closes the other half of a one-click convert nobody usually checks: the radar writes its equipment links under `relation: 'replaces'` and the deals function reads `.eq('relation', 'replaces')`, so a link written under any other label would exist and surface on no screen.

## Pre-Flight & Pitfalls

**Node 20 is mandatory — check this before believing any failure.** `engines.node` is `20.x` and
`.npmrc` sets `engine-strict=true`, so on any other major `npm install` aborts and leaves
`node_modules` **empty**. Everything downstream then fails for reasons that have nothing to do with
the cause: `tsc` bails before typechecking, `vitest` is absent, the app looks broken. `preinstall`
now blocks this (`npm run check:node`), but if you inherit a half-installed tree, `node -v` is the
first thing to check. Use `nvm use 20 && npm install`.

In a sandbox with no `nvm`, look for Node 20 on disk before concluding the suite
is unrunnable: this container ships it at `/opt/node20/bin` with a
`use-node-20` helper on PATH, while the default `node` is 22. Prefixing the PATH
(`export PATH="/opt/node20/bin:$PATH" && npm install`) installs cleanly and makes
`npm run check`, `npm run test`, `check:phantom-cols` and every other
tsx-dependent script work. Several rounds of this repo's history were written
under the belief that they could not be run at all, and a deleted handler's test
stayed red for a whole session because of it.

Before committing: `npm run check && npm run build && npm run format:write && npm run lint`.

Common mistakes:

0. Debugging a phantom broken repo on the wrong Node version (see above)
1. Missing `tenantId` filter (security)
2. Skipping Zod validation
3. Defining `requireAuth` locally instead of importing
4. Using `db:push` against production
5. Using `any` instead of fixing types
6. Missing TanStack Query loading/error states

Local dev browser login: export `VITE_SUPABASE_URL`/`VITE_SUPABASE_ANON_KEY` (from the server-side `.env` values) before `npm run dev` — the client crashes at boot without them. The dev CSP allows api/functions.printyx.net (server/index.ts). The anon keys currently in `.env`/`.env.example`/`wrangler.toml` are rotated/stale (GoTrue `/auth/v1/health` returns 401 with them); browser login needs a current anon key. Demo creds: `DEMO_USER`/`DEMO_PASSWORD` in `.env`.

Frontend endpoints must exist on BOTH backends: Express `server/routes-*.ts` serves dev, but prod hits the edge function directly — a query param (e.g. `?codes=`) supported only by Express silently breaks in production.

Billing edge fn (EDGE-002a): `/api/billing` is in `crmProxies`, so dev forwards the whole prefix to `supabase/functions/billing/` — full frontend parity lives there (`handlers/` per resource). The canonical billing schema audit is the header of `billing/handlers/_context.ts`: `billing_configurations`/`billing_cycles`/`billing_adjustments` are DRIFT tables (in no Drizzle schema/migration — raw-SQL-only legacy); handlers tolerate a missing relation (GET→`[]`, write→503) via `isMissingTableError`. The real `invoices` columns are `total_amount`/`amount_paid`/`balance_due`/`invoice_status`/`paid_date` — the legacy consolidated Express router referenced phantom cols (`balance`/`paid`/`total`/`tax`). `external_customer_id` doubles as the service-ticket id (`?ticketId=` filter). GET `/billing/invoices` returns `{ data, total }` — frontend consumers must use `extractRecords` (AdvancedBillingEngine crashed on `.map` before). Authenticated binary downloads use `client/src/lib/invoice-pdf.ts` (mirrors `quote-pdf.ts`); plain `fetch` has no Bearer header and 401s on edge functions. Cross-fn import `../email-marketing/_sendgrid.ts` is the accepted idiom (proposals fn does it). Stripe's live webhook URL is `/api/webhooks/stripe`, NOT under `/api/billing` — and that path is the GENERIC receiver in `server/integrations/webhook-routes.ts`, not the Stripe handler in `routes-subscriptions.ts`, which sits at `/api/subscriptions/webhooks/stripe`. INTEG-WEBHOOK-001 found the generic receiver's Stripe branch was a stub that verified the signature and discarded the event, so subscription state never moved from a real Stripe delivery; it now records to `inbound_webhook_events` and dispatches to `StripeService.handleWebhookEventEnhanced`. Two rules follow. A verified delivery is stored BEFORE anything acts on it, because a 2xx stops the provider retrying — never answer 200 from a handler that might not have persisted. And `verifyStripeSignature` enforces a 300-second replay window, matching `stripe.webhooks.constructEvent`; it did not before, so a captured signature was valid forever. AND UNTIL 2026-08-29 NONE OF THAT RAN: `/api/webhooks` is in `crmProxies`, the proxy registers at `routes-registry:297` and the receiver mounted at `:401`, so every inbound delivery went to the webhooks edge function, which calls `auth.getUser()` before routing - a provider sends no JWT, so Stripe and Google Calendar got 401, and the proxy falls through only on a NETWORK error, never a 401. The fix is ordering, not un-proxying: `inboundWebhookReceiver` (just `POST /api/webhooks/:provider`, with its rawBodyParser) is mounted BEFORE the proxy, while the health probe and outbound list stay proxied because the edge function owns them. It is safe because that edge function has `POST /`, `POST /:id/test` and `POST /:id/regenerate-secret` but NO `POST /:id`, so the shape was never contested. `server/tests/unit/inbound-webhook-ordering.test.ts` locks all of it, because ordering is invisible to tsc.

Accounts payable/receivable (EDGE-005a): the canonical tables are `accounts_payable` + `accounts_receivable` (shared/schema.ts, migration 0000) — their columns match the AccountsPayable.tsx / AccountsReceivable.tsx form fields exactly. The `account-payable`/`account-receivable` edge fns serve the FLAT URL shape the frontend calls (GET/POST `/`, GET/PUT/PATCH/DELETE `/:id`, plus `/summary`) and RETURN CAMELCASE rows (the pages read camelCase keys directly off the spread — snake renders blank). Prod resolves the plural `accounts-{payable,receivable}` segment via a `server.ts` route override → singular `account-*` dir; dev mirrors it through `crmProxies`. Earlier versions wrongly queried a phantom `bills` table (AP) and the E-Automate `invoices` table (AR) with nested URLs the frontend never called.

Quote math (QUOTE-016): `proposal_line_items.discount` is a DOLLAR amount off the whole line; `total_price` is stored NET of it, so the quote subtotal is automatically net and the quote-level discount applies after. Canonical formulas live in `shared/quote-math.ts` (replicated inline in the Deno proposals fn — keep in sync, locked by `server/tests/unit/quote-math.test.ts`). Guardrails evaluate the EFFECTIVE discount (`effectiveDiscountPct`: line + quote discounts over gross). Any discount requires `proposals.discount_reason` (+`_note`, migration 0019); the proposals edge fn POST/PATCH retry without those two columns on PGRST204 until the migration is applied. Banned structures, which imitate insight without carrying any: _"not just X, it's Y"_, _"not only X but Y"_, _"this isn't about X, it's about Y"_, _"No X. No Y. Just Z."_, the rule of three that goes abstract on the third item, the rhetorical question as a transition, and closing with a summary of what was just read. **At most one em dash** per piece of writing, never as the default connector; use commas, parentheses and semicolons. **Plain characters only.** Generated text carries Unicode that renders as ordinary punctuation, as ordinary whitespace, or as nothing at all, and it survives review precisely because it looks correct. **Anything a machine parses is ASCII unless the content requires otherwise**: code, config, JSON, YAML, CSV, SQL, regex, env values, filenames, URLs, commit subjects. Straight quotes `'` `"`, hyphen-minus `-`, three dots for an ellipsis, one ordinary space between words. Never emit curly quotes (U+2018/2019/201C/201D), en/em dashes (U+2013/2014), U+2026 ellipsis, U+2212 minus or U+2032 primes into code; a look-alike character in a PowerShell string or a SQL literal is a runtime failure, which is how `backup-databases.ps1` and `ssl-check.ps1` sat unparseable for months. Never emit a no-break space (U+00A0, and U+202F/2007/2009/2002/2003/3000), which breaks shell word-splitting, `grep` and column parsing while looking exactly like a space, or U+2028/U+2029, which are valid JSON and a syntax error inside a JS string literal. **Never emit an invisible or bidi character anywhere:** U+200B-U+200F, U+2060-U+2064, U+FEFF, U+00AD, U+034F, U+180E, the bidi controls U+202A-U+202E and U+2066-U+2069, and above all the Unicode tag block **U+E0000-U+E007F**, which encodes arbitrary ASCII invisibly and is the usual carrier for text a reviewer cannot see. Avoid homoglyphs (Cyrillic a/e/o/p/c/x, Greek omicron, fullwidth Latin, mathematical alphanumerics for bold): an identifier holding one compares unequal to the identifier it appears to be. Prose may use real typography and real accented names; prose may not carry characters that don't render. The one exception is a deliberate, load-bearing use, which carries a comment saying why. Scan with `rg -n '[\x{00AD}\x{034F}\x{061C}\x{180E}\x{200B}-\x{200F}\x{202A}-\x{202E}\x{2060}-\x{2064}\x{2066}-\x{2069}\x{FEFF}\x{E0000}-\x{E007F}]'`.
