## Critical Patterns

### Multi-Tenant Isolation (SECURITY CRITICAL)

- 4-tier hierarchy: Platform → Company → Regional → Location
- 8-level roles: Platform Admin (8) → Guest (1)
- Tenant resolution: `x-tenant-id` header → JWT `app_metadata.tenantId` → Session
- **Every query MUST filter by `tenantId`** — missing filters are security vulnerabilities.

```typescript
// CORRECT
await db.query.customers.findMany({ where: eq(customers.tenantId, tenantId) });

// WRONG — leaks across tenants
await db.query.customers.findMany();
```

### Authentication Middleware

**Never define `requireAuth` locally.** Import from centralized locations.

| Middleware            | Import From                             | Use Case                                  |
| --------------------- | --------------------------------------- | ----------------------------------------- |
| `requireAuth`         | `./replitAuth` or `./auth-setup`        | Standard (JWT + session fallback)         |
| `requireSupabaseAuth` | `./middleware/supabase-auth`            | Strict JWT only                           |
| `protectedRoute`      | `./middleware/supabase-auth`            | JWT + Auth + Tenant context (recommended) |
| `platformAdminRoute`  | `./middleware/supabase-auth`            | Platform admin only                       |
| `requirePermission`   | `./middleware/enhanced-rbac-middleware` | RBAC checks                               |

```typescript
import { requireAuth } from '../replitAuth';
import { getUserId, getTenantId } from '../utils/auth-helpers';

app.get('/api/resource', requireAuth, async (req, res) => {
  const tenantId = getTenantId(req);
  const data = await db.query.table.findMany({ where: eq(table.tenantId, tenantId) });
});
```

**Auth helpers** (`utils/auth-helpers`): `getUserId`, `getTenantId`, `isAuthenticated`, `isPlatformAdmin`.

### Unified Business Records

Leads and customers share `business_records`. Status field determines state. Lead-to-customer conversion = status update (preserves history).

TWO TABLES HOLDING ONE CONCEPT IS A COUNTING PROBLEM BEFORE IT IS A MIGRATION (COP-B00). `business_records` was declared canonical and nothing carried it out, and the story sat filed as a dev/prod disagreement until somebody counted: **53 edge functions read `business_records`; 7 touch `companies`, and three of those WRITE it** (`business-records`, `companies`, `import`). `business-records` is the function behind the production CRM account list and its own header calls itself "a backwards-compatible wrapper that delegates to the companies table", so an account created there lands where the opportunity radar, churn risk, QBR, contracts, invoices, service, search and the forecast never look. Count the readers and the writers before believing a story's framing - `grep -rln "\.from('<table>')" supabase/functions/ | sed 's|.*functions/||;s|/.*||' | sort -u` took seconds and changed what the story was. `npm run crm:reconcile` (COP-B00) is the tooling, and its design is the reusable part: it SEPARATES "does this row already exist over there" from "what would it look like there", and answers the first with EXACT keys only. An id match is proof; a `customer_number` match is proof because the column is UNIQUE on both; a NAME match is a CANDIDATE that is reported and SKIPPED, because COP-B10 and COP-B09 both record what it costs to let a migration decide unreviewed that two spellings are one thing - here it fuses two customer accounts. THE ID IS PRESERVED: `deals`, `proposals` and `quotes` all carry an account id, so copying under a fresh uuid orphans every reference the moment the readers switch, and keeping it makes the copy idempotent for nothing. NOTHING IS INVENTED TO SATISFY A NOT NULL - a row with no `created_by` is refused and counted rather than given a sentinel owner, and `source` is written as 'migrated' because the column's 'website' default would claim the account arrived through the web form. A free-text column mapped into a vocabulary (`companies.activity` -> `business_records.status`) COERCES BY RECORD TYPE and COUNTS the coercions in the report; the lead and customer vocabularies do not overlap, so 'qualified' on a customer row is a lead status on the wrong row. Runbook and what still needs the deployed database: `docs/COP-B00-crm-table-reconciliation.md`.

**Canonical CRM object model:** the CRM is mid-migration with duplicate models per entity. The canonical table for each entity (contact = `companyContacts`, company/account = `business_records`, pipeline = `deals` + `pipelineStages`/`pipelineTemplates`) and the deprecated duplicates + migration path are recorded in `docs/crm-canonical-model.md` (CRMX-002). Deprecated tables carry `@deprecated` banners. Bind new CRM work to the canonical tables only.

## Database

### Migration Workflow

1. Edit schema in `shared/`
2. `npm run db:generate` → creates SQL in `drizzle/migrations/`
3. Review the SQL
4. `npm run db:migrate` (acquires `__migration_lock`, auto-expires after 5min)
5. Commit schema + migration file together

**Journal integrity (SUPA-005):** drizzle's migrator only applies migrations listed in `drizzle/migrations/meta/_journal.json`. A `*.sql` file with no journal entry is silently NEVER applied → schema drift. `npm run check:migrations` (CI guard) fails when any migration file is unjournaled, two files share a 4-digit prefix, or journal `idx` is non-contiguous. Always add migrations via `db:generate` (which updates the journal) — never hand-drop a `.sql` into `drizzle/migrations/`.

**Snapshot integrity (COP-M00):** drizzle-kit diffs your schema against the snapshot of the LAST journal entry only. That snapshot went missing and `db:generate` silently re-emitted 445 statements of already-applied drift, numbered into a filename collision, so no schema change could ship. Fixed by capturing the drift as a real migration (`0057_cop_m00_schema_reconciliation.sql`, fully idempotent, 118 tables + 15 columns + 9 FKs) rather than absorbing it into a snapshot, which would have left 107 tables permanently un-migrated. `npm run db:generate` is now `scripts/db-generate.mjs`, which renumbers whatever drizzle-kit writes to (highest on-disk prefix + 1) and rewrites the journal tag — drizzle-kit names files from journal LENGTH, and the non-contiguous on-disk numbering is load-bearing (SUPA-002 sequenced `when` values so orphans sort after everything applied). `check:migrations` now HARD-fails when the last entry has no snapshot; the 25 mid-chain gaps stay a warned ratchet. `0057` is committed but UNAPPLIED anywhere — runbook in `docs/COP-M00-migration-tooling.md`. That doc also records the separate finding that `npm run db:migrate` cannot build a fresh database at all: it fails in migration `0000` on uuid-vs-varchar FK key columns and, being one transaction, creates nothing (PA-032).

A tenant_id COLUMN HAS TO BE ABLE TO HOLD A TENANT ID (AUDIT-032). `tenants.id` is `varchar PRIMARY KEY DEFAULT gen_random_uuid()`; 21 tables across four schema files declared `tenant_id integer NOT NULL`, so a read filtered on a real tenant gave **22P02** and an insert gave **42804** - both reproduced on Postgres 16, not inferred. Nothing caught it: tsc cannot, because the column type and the `tenantId` variable agree inside each file and the Express layer types `tenantId` as `any`; `check:phantom-cols` checks column NAMES, not types; and PostgREST leaves `.data` null on error while this code writes `?? []` around it, so the symptom was an EMPTY DASHBOARD, indistinguishable from a table nobody has filled in. That is why six of them - `client_collected_metrics`, `contract_renewal_tracking`, `renewal_analytics`, `supply_monitoring`, `supply_replenishment_analytics`, `supply_usage_history` - sat in `docs/unwritten-tables-baseline.json` as tables nothing writes to, when the truth is that nothing COULD. The affected features are auto-supply replenishment, contract renewal (including the routed `/contract-renewal-autopilot`), document automation and the printyx-client agent. Migration `0062_round_sway.sql` converts all 21 and was PROVEN by applying it to a real Postgres twice, including against a database that had already run the hand-run `_inbound_webhook_events.sql` (which drizzle-kit correctly folded in, since an unjournaled file is invisible to the snapshot - it is `IF NOT EXISTS` for that reason). `npm run check:tenant-id-types` gates both sides at zero, because either alone is wrong here: it reads the Drizzle declarations AND replays the migration chain in journal order, since `0000` creates these columns as integer and `0062` converts them. The workaround the bad type forced is the thing to recognise elsewhere: `predictive-service-dispatch-service.ts` did `eq(clientCollectedMetrics.tenantId, parseInt(tenantId))` to satisfy tsc, and `parseInt` of a uuid is its leading digits (`'550e8400-...'` -> 550) or NaN, so it filtered on a tenant that does not exist. When a tenant id needs coercing, the column is wrong, not the id.

**A scratch Postgres is available, and several "blocked on DB access" stories are not (COP-M07):** this container ships PostgreSQL 16 at `/usr/lib/postgresql/16/bin`. `initdb` refuses to run as root, so run it as the `postgres` user (`su postgres -c "... initdb -D <dir> -U postgres --auth=trust"`), start it on a spare port, apply the migrations statement-tolerantly (`psql -v ON_ERROR_STOP=0 -f` in journal order — `db:migrate` itself dies in `0000`, see above), then insert one `tenants` + `users` row and run `DEMO_USER=<email> npm run seed:demo`. That is enough to verify anything that needs real rows. Two traps it exposes: the demo seeder short-circuits with "Demo data already exists" for a tenant that has any, and `generateId()` produces TENANT-INDEPENDENT ids (`stage-demo-001`) under `onConflictDoNothing`, so seeding a SECOND tenant into the same database reports success and writes NOTHING. Use a fresh database per tenant you want to seed.

**Pipeline stages (COP-M07):** `deals.stage_id` holds a LEGACY `deal_stages.id`; `pipeline_stages.legacy_stage_id` is the bridge CRMX-005 established. `npm run check:stage-resolution` (needs `DATABASE_URL`) asserts every deal resolves to exactly one canonical stage and exits **2** when it cannot connect, so "did not run" is never read as "passed" — run it before and after touching any stage writer. Three defects this closed, each reproduced against a real database: `pipeline_templates.pipeline_type` is NOT NULL and the lazy bootstrap in `supabase/functions/pipeline-config/index.ts` omitted it, so that bootstrap could NEVER succeed and any tenant without a template had a permanently empty board; the explicit template create wrote `stage_type` and `allowed_transitions`, neither of which is a column on `pipeline_stages`, so every create returned "Template saved but stage insert failed" and orphaned the template; and the read paths returned raw rows, so the Stage Type select always showed its placeholder. `stageType` now maps to `is_final_stage`/`is_closed_won`/`is_closed_lost`/`is_active` through `supabase/functions/_shared/pipeline-stage-type.ts`. `allowed_transitions` was dropped rather than given a column — nothing reads it.

`db:push` is dev-only. For an existing DB without migrations: generate baseline, then `npm run db:migrate:baseline` (marks applied without executing).

### Edge path normalization (prod-only 404s) — READ BEFORE TOUCHING ANY EDGE FN

An edge handler NEVER sees its own name in the path. The Coolify dispatcher
(`supabase/functions/server.ts`) resolves the function from URL segment 0 and then
**strips it** (`stripSegments = 1`; it rewrites to `'/' + pathParts.slice(1).join('/')`)
before invoking the handler. So `functions.printyx.net/seo/settings` arrives as
`/settings`.

Therefore **`const resource = url.pathname.split('/').filter(Boolean)[1]` is a bug.**
It reads `undefined`, every `resource === '...'` guard is false, and the function 404s
on EVERY route. Always use the idempotent helper instead — it strips an OPTIONAL
leading prefix, so routing is identical whether the segment is present or already gone:

```typescript
import { normalizePath } from '../_shared/path.ts';
const { parts } = normalizePath(url.pathname, 'seo'); // parts[0] = resource
```

**This is invisible in dev.** If the prefix is not in `crmProxies`, Express serves it
locally and the edge function is never exercised — the outage is prod-only. ALL 169 edge functions are now migrated (2026-07-17); `npm run check:edge-paths` enforces it at 0. seo and deal-desk were each 404ing on EVERY endpoint before that sweep. The impact claim is statically derived — the mechanism is proven but nothing was executed against a deploy, so confirm with one curl per prefix before treating it as an incident writeup.

GPT-5 endpoints (AI-001): `/api/ai/gpt5/*` is served by `supabase/functions/ai-gpt5/` — a `server.ts` alias (`functionName === 'ai' && subPath[0] === 'gpt5'`) plus a `crmProxies` entry `'/api/ai/gpt5': { fn: 'ai-gpt5', pathPrefix: '/gpt5' }`. Only that sub-path is proxied; the rest of `/api/ai` stays on Express and has no frontend caller. Prompt text, model configs and the response parser are duplicated in `_shared/gpt5-prompts.ts` (+ `_shared/crisis-response.ts`) and locked to `server/services/gpt5-service.ts` by `server/tests/unit/gpt5-prompts-parity.test.ts`. The edge fn needs `OPENAI_API_KEY` in the edge environment or every endpoint 500s. Two traps this closed: the Responses API `output` is an ARRAY (`response.output?.content` is always undefined — use `extractResponseText`, since the raw REST payload carries no `output_text`), and `check:routes` classifies per DOMAIN, so a multi-segment proxy prefix only counts when EVERY live frontend path under that domain sits inside it — `route-parity.mjs` now enforces that rather than whitelisting.

Phantom PostgREST columns (COP-M01): edge functions name columns in STRINGS, so a column that does not exist is a runtime 42703 — a 500 the moment the code path runs — invisible to tsc, lint and any test that does not hit a database. `npm run check:phantom-cols` (`scripts/check-phantom-columns.ts`) reads all 671 Drizzle tables and checks every column literal an edge fn hands to PostgREST (`.eq/.order/.or/.select` and INLINE `.insert/.update` object literals) against the table its call chain is on; baseline `docs/phantom-columns-baseline.json` at **384**, do not grow it. Known blind spots, stated so a pass is never read as proof of correctness: payloads built as a named variable (the deals insert was one), runtime-assembled names, camel→snake field maps, the 107 tables in no Drizzle schema, and 15 tables declared twice with different shapes (skipped as ambiguous rather than reported — that is `check:dup-tables`' story). ## Pre-Flight & Pitfalls

**Node 20 is mandatory — check this before believing any failure.** `engines.node` is `20.x` and
`.npmrc` sets `engine-strict=true`, so on any other major `npm install` aborts and leaves
`node_modules` **empty**. Everything downstream then fails for reasons that have nothing to do with
the cause: `tsc` bails before typechecking, `vitest` is absent, the app looks broken. `preinstall`
now blocks this (`npm run check:node`), but if you inherit a half-installed tree, `node -v` is the
first thing to check. Use `nvm use 20 && npm install`.

In a sandbox with no `nvm`, look for Node 20 on disk before concluding the suite
is unrunnable: this container ships it at `/opt/node20/bin` with a
`use-node-20` helper on PATH, while the default `node` is 22. Prefixing the PATH
(`export PATH="/opt/node20/bin:$PATH" && npm install`) installs cleanly and makes
`npm run check`, `npm run test`, `check:phantom-cols` and every other
tsx-dependent script work. Several rounds of this repo's history were written
under the belief that they could not be run at all, and a deleted handler's test
stayed red for a whole session because of it.

Before committing: `npm run check && npm run build && npm run format:write && npm run lint`.

A CALENDAR DATE IS NOT AN INSTANT, AND THE RULE IS NOW WRITTEN DOWN (DATE-LOCAL-002). Several columns here are `timestamp` in the schema but hold a CALENDAR DATE - `meter_readings.reading_date`, `time_entries.entry_date`, `tasks.due_date`, `invoices.invoice_date` and `paid_date`, journal entry dates, contract start and end. DATE-LOCAL-001 made the client write them as a local `yyyy-MM-dd`, so Postgres stores MIDNIGHT. A bound built from `new Date()` carries a time of day, so the comparison lands half a day off and the window is wrong by exactly one day, silently, in whichever direction the operator points. **The rule: a range filter on a calendar-date column is snapped to a day boundary - `startOfUtcDay` for a lower bound, `startOfNextUtcDay` with a strict `.lt()` for an upper one, both from `supabase/functions/_shared/date-months.ts`. An instant column (`created_at`, `resolved_at`, `triggered_at`) is compared to an instant and needs none of this.** Prefer the exclusive next-day bound over an inclusive `23:59:59.999`, which is a real timestamp a row can exceed. SPREADING A REQUEST BODY INTO POSTGREST IS TWO DEFECTS IN ONE LINE (COP-M01). `.update({ ...body, updated_at })` lets the BODY decide every column name, and it lets the body name columns the caller should never set. `PUT /leads/:id` was exactly this: LeadDetail sends 30 camelCase fields, PostgREST wants columns, so every save was a PGRST204 surfaced as "Failed to update lead" - **in production only**, because `/api/leads` is not proxied and dev goes through `storage.updateLead` -> Drizzle, which maps field names to columns. A TENANT-SCOPED WRITE IS BOUND IN THE PAYLOAD OR IN THE FILTER, AND THEY ARE DIFFERENT RULES (SEC-TENANT-005). `check:insert-tenant-id` now covers all four verbs. INSERT and UPSERT need `tenant_id` in the payload: a NOT NULL column fails the write outright (the first save of accessibility settings 500'd for every user), and a nullable one writes a row no tenant-filtered read can ever see, so the user is told it saved and it is gone. UPDATE and DELETE do not need it in the payload at all - they need it in the FILTER, or the write reaches ANOTHER TENANT'S ROW, which is what SEC-TENANT-001 found in parts-orders. An id is not a substitute: these are uuids, so guessing one is impractical, but they travel in URLs, exports and support tickets, and hard-to-guess is not an authorisation check. THREE THINGS COUNT AS BOUND for an update or delete, and the guard knows all three: a `tenant_id` filter on the chain; a write scoped to the authenticated user (`.eq('user_id', user.id)` cannot cross a tenant, because a user is in one); or a PRECEDING OWNERSHIP READ of the same table filtered by id AND tenant_id that 404s when absent, which is what saved-views does.
