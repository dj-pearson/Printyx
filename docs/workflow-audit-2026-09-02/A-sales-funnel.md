# Sales Top-of-Funnel Audit (lead identification, nurturing, CRM outreach)

Scope per assignment: routes from `client/src/App.tsx` / `client/src/components/layout/RoleAwareCollapsibleSidebar.tsx` covering leads, prospects, contacts, companies, customers, lead map, auto-routing, sales-rep assignments, Apollo, data enrichment, outreach, marketing sequences/forms, email autopilot, autopilot, import, demo scheduling, booking pages, calendar, CRM goals. All findings below were verified by reading the cited file/line; anything not directly read is marked UNVERIFIED.

## Headline finding (read this before the table)

**Production runs two parallel, disconnected "lead" data planes, and the split is invisible from any one file.**

- **UI plane — table `companies`.** `LeadsPage.tsx` (`/leads`, `/leads-management`) reads `/api/companies?recordType=Lead` directly (`client/src/pages/LeadsPage.tsx:300-303`). `CrmLeadsPage.tsx` (`/crm/leads`) reads `/api/business-records`, which is a wrapper that **lists, creates, updates and deletes against `companies`**, not `business_records` (`supabase/functions/business-records/index.ts:1-3,281-356,445-477` — this is COP-B00's already-documented finding). `ProspectsPage.tsx` and `CustomersPage.tsx` both call `/api/companies` / `/api/companies/stats` directly. `Contacts.tsx` bypasses both Express and the edge function and queries `companies` straight from the browser via the Supabase JS client (`client/src/pages/Contacts.tsx:210-225`).
- **Automation plane — table `business_records`.** The **separate** `leads` edge function (`supabase/functions/leads/index.ts`) — which serves `LeadDetail.tsx` (`/leads/:slug`) and `LeadMapViewer.tsx` (`/lead-map`) — reads and writes `business_records` exclusively (`supabase/functions/leads/index.ts:88-92,268-274,304-306`). `auto-lead-routing` (`supabase/functions/auto-lead-routing/index.ts:398,435`) and `sales-rep-assignments` (`supabase/functions/sales-rep-assignments/index.ts:135,150,219,256`) both read/write `business_records.owner_id`/`assigned_sales_rep`. Apollo's "Add to CRM" writes a **new** `business_records` row (`supabase/functions/apollo/index.ts:115-142`). The public web-form pipeline (`server/services/web-form-processor.ts:59-110`, an in-process Node worker started in `server/index.ts` on a 30s timer) inserts captured leads into `businessRecords` via Drizzle, then runs real lead-scoring and auto-routing service calls on that same row (confirmed in `prd.json` CRMX-011 notes).
- **These are two different tables with independently-generated UUIDs; nothing keeps their ids in sync.** `scripts/migrate-business-records-to-companies.ts` is a static-code-reference rewriter (renames source-code identifiers), **not a data migration** — it never copied rows or preserved ids (confirmed by reading the whole 430-line file; no `.insert`/`INSERT INTO` against `companies` appears anywhere in it).

Consequences, each independently verified:

1. **Every lead captured by a web form, or added via Apollo, is invisible on every sales-rep screen in scope** (`/leads`, `/leads-management`, `/crm/leads`, `/prospects`, `/customers`) because all of those read `companies`, and web-form/Apollo leads land only in `business_records`.
2. **Clicking a lead row in `CrmLeadsPage` is very likely to hard-fail.** `CrmDataTable` navigates to `` `${config.detailPath}/${record.id}` `` (`client/src/components/crm/CrmDataTable.tsx:477,482,518`); `leadsConfig.detailPath` is `/leads` (`client/src/lib/crm-object-registry.ts:330`) and `record.id` is a `companies.id` (the list source). `LeadDetail.tsx` then fetches `/api/leads/${id}` (`client/src/pages/LeadDetail.tsx:250-251`), which looks the id up in `business_records` (`supabase/functions/leads/index.ts:268-274`) and returns 404 `Lead not found` unless that id coincidentally also exists as a `business_records` row.
3. **Lead scoring and auto-routing run only on data the sales UI never shows.** Both operate on `business_records` (see above); reps managing leads through `companies`-backed pages get no score, no BANT, no auto-assignment.
4. **CRMX-011 ("Web forms → lead creation + scoring + routing") is marked `passes: true` in `prd.json` but its output is invisible to reps today**, because the story landed 2026-07-14 — three weeks before COP-B00 (2026-08-11) recorded that the sales UI runs on `companies`. Nobody has gone back to reconcile the two.

This is the same root cause COP-B00 already opened (production runs `companies`, docs say `business_records` is canonical), but COP-B00's own text is scoped to the `business-records` edge function itself. The fan-out documented above — that `leads`, `auto-lead-routing`, `sales-rep-assignments`, Apollo, and the web-form pipeline all independently chose the _other_ side of the split — has not been recorded anywhere in `prd.json` before this audit. It is the single most damaging defect in this scope and blocks or hollows out most of questions (b)–(f) below.

## 2. Workflow-stage gaps

**Lead identification** (web forms, Apollo, manual entry, CSV import):

- _Exists_: web-form capture → dedupe → lead creation → scoring → auto-routing → `form.submitted` workflow dispatch, all real (CRMX-011). Apollo search/enrich/add-to-crm exists.
- _Missing_: the captured lead never reaches any sales-rep-facing list page (headline finding). `apollo-leads` page's bulk-add and stats calls have no backend match.
- _Built but unreachable_: `data-enrichment` edge fn (dead duplicate of `enrichment`); `dedup-companies`, `customer-segments`, `business-records-search` edge functions (no caller anywhere).
- _No handoff_: nothing reconciles a `business_records` lead against an existing `companies` account, so the same prospect can exist as two unrelated rows with no dedupe across the table boundary.

**Lead nurturing** (scoring, sequences, outreach):

- _Exists_: `lead-scoring` edge fn (rules/calculate/BANT/engagement/analytics) is a complete implementation; `lead-intelligence-service.ts` runs it automatically for web-form leads. `email-sequences` enroll/unenroll state machine is correct and idempotent (CRMX-009). Real SendGrid sending exists (`email-service.ts`), driven by an in-process Node interval (`email-sequence-scheduler.ts:335-337`) started from `server/index.ts`.
- _Missing_: no UI ever calls `lead-scoring`'s manual `calculate`/`score`/`grade`/`leaderboard` endpoints, and the one component built for it (`BANTAssessment.tsx`) is never imported by any page — a fully-built orphan.
- _Built but unreachable_: scoring only ever fires on `business_records` rows the sales UI can't see.
- _Depends on infra assumption not verified here_: the sequence-send scheduler and the web-form processor are both `setInterval` timers requiring the Node server process to run continuously in production as a background worker (consistent with CLAUDE.md's description of the workflow-runtime "boot-started sweeper," but not independently confirmed against a live deployment in this audit — UNVERIFIED).
- _No handoff_: sequence enrollment has no wiring from the Leads/Prospects UI in scope — `EmailSequencesPage.tsx` is a standalone campaign-management screen, not a "enroll this lead" action on `LeadDetail`/`LeadsPage`/`CrmLeadsPage` (UNVERIFIED whether any other in-scope page triggers enrollment; none of the files read here do).

**CRM outreach** (Outreach Hub, 1:1 email autopilot):

- _Exists and works_: the AI Outreach Hub (business context, specialty, sequence studio, draft generator) is fully implemented end to end.
- _Missing_: 1:1 rep email autopilot (`/sales/email-autopilot`) cannot actually send email or read a real inbox — draft generation may work but the whole point of the feature (send-from-Printyx) is stubbed (open stories PA-043, CRMX-010, COP-B07).

**Lead → deal conversion**:

- _Exists_: `LeadsPage`'s "Convert to Prospect" row action, but this only PATCHes `companies.business_record_type` to `'Prospect'` — it is a status change, not a deal.
- _Exists but broken/unlinked_: `LeadDetail.tsx`'s "Create Deal" CTA dispatches a `leadTabAction` custom event (`LeadDetail.tsx:507-515`) that `LeadDeals.tsx` listens for (`LeadDeals.tsx:105-142`) and opens a create-deal dialog that POSTs `leadId`/`companyId` fields the `deals` table has no column for — both are silently dropped on insert (`supabase/functions/deals/index.ts:818-824` has no `leadId`/`companyId` mapping). The tab's own list query (`GET /api/deals?leadId=`) is also ignored by the edge fn (no such filter exists), so it would show every deal in the tenant, not the lead's. In practice this whole flow is moot because `LeadDetail.tsx` itself can't load real lead data (headline finding #2).
- _Missing entirely_: there is no endpoint or UI action anywhere in scope that reads a `companies`/lead row and creates a `deals` row with a resolvable `stage_id` **and** a durable link back to the source lead. `deals.stage_id` resolution itself is solid (COP-M01's `_shared/deal-stage.ts` resolves a slug to a real `pipeline_stages`/`deal_stages` id at request time), but nothing in this scope calls it starting from a lead.

## 4. Proposed stories

1. **Reconcile the leads automation plane onto the same table the sales-rep UI reads (or vice versa)**
   As a sales rep, I need a lead captured by a web form or Apollo to show up on my Leads list, because right now it never does.
   AC: (a) one of `companies`/`business_records` is chosen as the single write target for lead creation across `leads` edge fn, `auto-lead-routing`, `sales-rep-assignments`, `web-form-processor.ts`, and Apollo's add-to-crm; (b) `CrmDataTable`'s row navigation from a `companies`-sourced list resolves successfully in `LeadDetail.tsx` for every row, verified by an integration test that creates a lead through each entry point and asserts it is visible through every other; (c) `docs/crm-canonical-model.md`'s COP-B00 addendum is updated to record this fan-out; (d) `check:phantom-cols`/`check:phantom-tables` pass unchanged.
   Priority: 1. dependsOn: COP-B00 (blocking, already open).

2. **Add `lead_routing_rules` as a real migrated table**
   As an admin, I need to create lead-routing rules, because the feature 503s today.
   AC: (a) `shared/*.ts` gets a `leadRoutingRules` pgTable matching the columns `auto-lead-routing/index.ts` already expects; (b) a generated migration (via `db:generate`, per COP-M00's tooling) adds it; (c) `GET/POST/PUT/DELETE /api/auto-lead-routing/rules` return real data instead of 503 `ROUTING_RULES_UNAVAILABLE`; (d) `npm run check:phantom-tables` baseline does not grow.
