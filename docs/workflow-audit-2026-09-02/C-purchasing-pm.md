## 2. Workflow-stage gaps

**Stage: Closed deal → lease-or-payment check → handoff to Purchasing & PM**

- **What exists:** `contracts.tsx` has a "Book Order" action on every contract row that navigates to `/purchase-orders?contractId=${contract.id}` (`client/src/pages/contracts.tsx:610-617,683-689`). A complete, richly-modeled handoff schema exists (`sales_handoff_checklists` with `opportunityId`/`contractId`/`customerId`, `accountProfile`, `equipmentDetails`, `installationPlanning` — `shared/sales-handoff-schema.ts:18-186`), plus `handoff_task_templates`, `handoff_tasks`, and `implementation_projects` (customerId + handoffId + milestones/risks/issues) — all real tables (migration 0000) with edge functions that mostly compile against the correct schema (except `sales-handoffs` itself, which queries a phantom table name).
- **What is missing:** There is **no dashboard, queue, or list anywhere in any client tree** that shows "deals/contracts that closed and need equipment ordered." The only UI entry point is the per-contract "Book Order" button, which is not gated by contract status (shows on every contract, signed or not) and has no idempotency (nothing marks a contract as "PO already created").
- **What is built-but-unreachable:** The entire `sales_handoff_checklists` → `handoff_task_templates`/`handoff_tasks` → `implementation_projects` pipeline. This is precisely the mechanism a purchasing/operations person would use to see "what needs ordering," and it is 100% dead code — no page, no button, no cross-function fetch references any of its four edge functions.
- **State transition that does not exist:** "Book Order" navigates to `/purchase-orders?contractId=X`, but `PurchaseOrders.tsx` only renders `contractId` as a read-only text hint (`PurchaseOrders.tsx:482-489`) — it is never added to the create-PO form schema (`purchaseOrderFormSchema`, `PurchaseOrders.tsx:84-109`) and never sent in `createPOMutation`'s POST body (`PurchaseOrders.tsx:204-206`). The `purchase_orders` table itself has no `contract_id`/`deal_id`/`opportunity_id` column at all (`shared/schema.ts:6786-6856`). **Once a PO is created, there is no way — anywhere in the schema — to trace it back to the deal/contract that caused it.**

**Stage: Purchase order creation → approval**

- **What exists:** A full status state machine (`draft → pending_approval → approved → ordered → partially_received/received`, `supabase/functions/purchase-orders/index.ts:8-16,950-983`) with submit/approve/reject/receive actions, all now writing to real columns after the AUDIT-037 migrations (`0065`, `0066`).
- **What is missing:** Line items entered in the create dialog are never persisted — the frontend sends key `items`, the edge fn reads only `lineItems`/`line_items` (`PurchaseOrders.tsx:98-109` vs `supabase/functions/purchase-orders/index.ts:761`) — so `subtotal` is always computed as 0 server-side and no rows are ever written to any line-item table on create through this UI path.
- **What is built-but-unreachable/broken:** The entire `/purchase-orders/:id/line-items` sub-resource (GET/POST/PUT/DELETE) targets `purchase_order_line_items`, a table that exists in no migration (verified: `grep -rln "purchase_order_line_items" drizzle/migrations/*.sql` = 0 hits). The real line-item table is `purchase_order_items` with a much narrower column set. This means: (a) the line-items sub-endpoints 42P01 on every call, (b) the `/receive` endpoint's line-item-quantity bookkeeping (`index.ts:536-590`) can never find any rows, so **"receive against a PO" is non-functional end to end**, not merely unwired.
- **State transition that does not exist:** approve → automatic accounts-payable bill. `accounts_payable.purchase_order_number` is a free-text varchar (`shared/schema.ts:6641`), not an FK; nothing creates an AP row when a PO is received.

**Stage: Approved PO → order placed with manufacturer**

- **What exists:** A complete, purpose-built EDI/ordering schema and edge function: `manufacturer_connections`, `manufacturer_orders` (with a genuine `purchase_order_id` column, migration `0000:4943-4973`), `manufacturer_order_line_items`, `manufacturer_order_confirmations`, `manufacturer_order_shipments`, `manufacturer_order_exceptions`, served by a 145-line dispatcher plus 7 handler files under `supabase/functions/manufacturer-orders/`.
- **What is missing:** Any UI. Zero callers in any of the seven client trees. `PurchaseOrders.tsx`'s only downstream action from `approved` is "Release to Warehouse" (`PurchaseOrders.tsx:1021-1033`), which does not touch this subsystem at all.
- **What is built-but-unreachable:** The whole manufacturer-ordering subsystem — the natural next step after PO approval for a dealer that orders equipment from Canon/Xerox/etc. via EDI rather than a generic vendor PO.

**Stage: PO approved → released to warehouse → equipment onboarding checklist**

- **What exists:** This is the one leg of the whole scope that is genuinely wired end to end. `PurchaseOrders.tsx` → "Release to Warehouse" → `/warehouse-operations?orderId=X` (`PurchaseOrders.tsx:1026,1224`) → `WarehouseOperations.tsx:848` links to `/onboarding/enhanced?orderId=${orderId}` → `EnhancedOnboardingForm.tsx:455-462` reads `orderId`/`quoteId` from the URL and the `onboarding` edge fn persists them onto `equipment_onboarding_checklists.order_id`/`.quote_id` (`supabase/functions/onboarding/index.ts:396-397`), which are documented as "links to purchase order if available" (`shared/schema.ts:3695`).
- **What is missing:** This chain is not covered by any automated test and depends on a human clicking through three separate pages; there is no server-side guarantee the checklist actually gets created (nothing marks a released PO as "onboarding started").

**Stage: Task/project management for purchasing & implementation work**

- **What exists:** `TaskHub.tsx` provides tasks + a lightweight "Projects" tab over the generic `projects` table (`customerId` only — no contract/deal link, since migration `0002` dropped `contract_id`/`project_manager`/etc. from that table; see Defect D5). `task-workflows` is a separate, working, template-driven checklist engine (`task_workflows`/`task_workflow_steps`/`task_workflow_events`, migration `0009`) reachable at `/workflows`.
- **What is missing:** Tasks cannot be linked to a customer through the API even though the column exists (`tasks.customer_id`, `shared/task-schema.ts:96`, never mapped in `supabase/functions/tasks/handlers/tasks.ts:113-134`). No task/project can be linked to a purchase order, a manufacturer order, or a contract — there is no `related_to_type`/`related_to_id` polymorphic column anywhere in `task-schema.ts`.
- **What is built-but-unreachable:** The richer `implementation_projects` model (milestones, risks, issues, `handoffId`, `customerSatisfaction`) sits idle while the reachable `projects` tab is a bare name/status/budget/hours record with no PM tooling.

**Stage: Automation / triggered workflows on PO or task events**

- **What exists:** A 15-table, DB-persisted, sweeper-resumed workflow runtime (`server/services/workflow-execution-service.ts` + `workflow-runtime.ts`) that genuinely dispatches on `deal.stage_changed`, `record.created`/`record.updated`, and `form.submitted` (per CLAUDE.md and confirmed unchanged — `dispatchWorkflowEvent`/`dispatchWorkflowEventSafe` call sites were not re-verified line-by-line in this pass but the claim in CLAUDE.md was cross-checked against the still-live 401 state of the management UI below).
- **What is missing:** No event seam anywhere fires on a PO status change, a manufacturer order confirmation, or a task/project state change — the three dispatch call sites named in CLAUDE.md (`supabase/functions/deals/index.ts`, `supabase/functions/business-records/index.ts`, `server/services/web-form-processor.ts`) do not include purchasing or PM domains.
- **State transition that does not exist / confirmed still broken:** `server/routes/workflow-automation-routes.ts` — every one of its handlers reads only `req.session.user` for identity, which nothing in the codebase ever sets (`:8-27` header, `:58,83,100,132,161` 401 returns, re-verified in this pass). No UI anywhere can create, inspect or approve a workflow. This is the existing open story CRMX-008a (passes=false, priority 3) — not new, but confirmed still current.

## 3. Defects found

**D1 — `purchase_order_line_items` is a phantom table; PO line items and receiving are non-functional.** Severity: **High**. `supabase/functions/purchase-orders/index.ts` queries/writes `purchase_order_line_items` in 19 places (lines 79, 126, 162, 266, 278, 327, 371, 546, 559, 594, 629, 739, 859, 869, 1004, 1036, 1050, 1084, 1345). That table exists in no migration (`grep -rln "purchase_order_line_items" drizzle/migrations/*.sql` returns nothing) and is not in `docs/phantom-columns-baseline.json` (checked programmatically — absent). The real table, `purchase_order_items` (`shared/schema.ts:6858-6883`), has a much narrower column set (`line_number`, `item_description`, `item_code`, `quantity`, `unit_price`, `total_price`, `received_quantity`) than the columns the handler writes (`inventory_item_id`, `part_number`, `manufacturer_part_number`, `quantity_ordered`, `quantity_received`, `unit_of_measure`, `unit_cost`, `total_cost`, `last_received_date`). Renaming alone would not fix it — the columns don't exist either. Consequence: the entire `/purchase-orders/:id/line-items` sub-resource 500s, and the `/receive` endpoint can never find line items to reconcile, so **"mark a PO received"** never actually updates quantities. Not covered by AUDIT-037 (which fixed 17 references on the `purchase_orders`/`purchase_order_items` tables themselves, explicitly excluding this second table — see AUDIT-037's own description, "PURCHASE_ORDERS AND PURCHASE_ORDER_ITEMS, 17 references"). **New finding, not covered by any open prd.json story.**

**D2 — PO create form silently drops all line items.** Severity: **High**. `PurchaseOrders.tsx`'s form schema uses the key `items` (`PurchaseOrders.tsx:98-109`) and posts the whole form object as-is (`PurchaseOrders.tsx:204-206`). The edge fn's create handler reads only `body.lineItems || body.line_items` (`supabase/functions/purchase-orders/index.ts:761`), which is always `undefined`/`[]` for this caller, so `subtotal` is computed as 0 (`index.ts:762-772`) and the `if (lineItems.length > 0)` guard (`index.ts:833`) never inserts any items. The user sees a "Purchase order created successfully" toast (`PurchaseOrders.tsx:213-217`) with no indication the items they entered were discarded. Combines with D1: even if the key name were fixed, the target table doesn't exist. **New finding.**

**D3 — No linkage from a closed deal/contract to the purchase order it produces.** Severity: **High**. `purchase_orders` has no `contract_id`/`deal_id`/`opportunity_id` column (`shared/schema.ts:6786-6856`, confirmed against migrations 0000, 0001, 0065, 0066 — none add such a column). `contracts.tsx`'s "Book Order" button (`:610-617,683-689`) passes `contractId` only as a query string that `PurchaseOrders.tsx` renders as inert text (`:482-489`) and never persists. There is no way, after the fact, to answer "which PO(s) came from this contract" or "which contract does this PO belong to." **New finding** — related to but distinct from AUDIT-037 (which was about wrong column _names_, not a missing linkage column).

**D4 — No operational view of "closed deals needing equipment ordered."** Severity: **High**. Confirmed by exhaustive route/page search: no page in `client/src/pages` lists contracts/deals by an "equipment not yet ordered" or similar status. The purpose-built mechanism for this (`sales_handoff_checklists` → `handoff_tasks`/`handoff_task_templates` → `implementation_projects`) is fully modeled in the database (migration 0000) and served by four working-or-mostly-working edge functions, but has zero callers anywhere (confirmed against `docs/unreferenced-edge-fns-baseline.json`, all four already listed there). **Not new as an "orphan edge fn" finding (already baselined), but the specific consequence — there is no purchasing queue at all, and the exact mechanism to build one already exists server-side — had not been stated.**

**D5 — Task/project tools cannot link work to the entity a purchasing/PM person actually cares about.** Severity: **Medium**. `tasks.customer_id` is a real column (`shared/task-schema.ts:96`) that the create/update mapper in `supabase/functions/tasks/handlers/tasks.ts:118-134` never sets — only `assigned_to` and `project_id` are mappable, so a task cannot be tied to a customer via the API despite the column existing. Separately, the `projects` table lost `contract_id`, `project_manager`, `estimated_budget`/`actual_budget`, `color`, `template`, `workflow`, `tags`, `custom_fields`, and `completed_at` in migration `0002` (see AUDIT-039's withdrawal notes) — the reachable "Projects" tab in TaskHub can link a project only to a `customerId`, nothing else. **New finding for the `tasks.customer_id` half; the `projects` column history is documented in AUDIT-039 (already resolved/closed, not open).**

**D6 — No approval-permission enforcement on purchase orders in production; inconsistent/broken enforcement in dev.** Severity: **High** (security). Production's `purchase-orders` edge function performs auth+tenant checks only — no role or permission check anywhere in the file (grep for `role`/`level`/`permission` returns nothing) — so **any authenticated member of a tenant can approve, reject, or cancel any purchase order of any dollar amount**, regardless of their actual role. Dev's Express equivalent (`server/routes-purchase-orders.ts`, mounted via `routes-registry.ts:401`) gates every route on `PERMISSIONS.INVENTORY.PURCHASE_ORDER.*`, which resolves to `inventory.po.view/create/edit/delete` (`server/middleware/rbac-route-helper.ts:210-216`) — codes that **no seeded role holds** (`grep -c "'inventory.po" rbac-seeder.ts` = 0), so every non-platform-admin user is denied in dev. Meanwhile the sidebar and the seeded System B permissions use a _third_, unenforced vocabulary (`operations.po.view/create/approve`, held by `OPERATIONS_MANAGER` at `rbac-seeder.ts:1834-1835` and others) that governs only what shows in navigation, not what the API allows. **Already flagged generically** — `purchase-orders` is present in `docs/edge-rbac-baseline.json` — but the three-vocabulary mismatch and the specific consequence (dev locks out real purchasing roles; prod has no gate at all) had not been spelled out.

**D7 — `/workflows` (task-workflow templates/instances) has no navigation-permission entry at all.** Severity: **Medium**. Every other route audited here has a `navigation-permissions.ts` entry (even if permissive, `alwaysVisible: true`); `/workflows`, `/workflows/new`, `/workflows/:id`, `/workflows/:id/edit`, `/workflows/:id/steps/:stepId` have none (`grep -n "'/workflows'" client/src/lib/navigation-permissions.ts` = 0 hits). Depending on how the sidebar/route-guard treats an absent key (UNVERIFIED — not traced further in this pass), this page family is either invisible to everyone or visible to everyone regardless of role; either way it is inconsistent with every sibling page. **New finding.**

**D8 — Two full vendor-CRUD pages for one table.** Severity: **Low**. `/vendors` (`Vendors.tsx`) and `/vendor-management` (`VendorManagement.tsx`) are both live, both routed, both hit the same `vendors` edge function, and both were independently fixed for the same phantom-shape bug in QUALITY-002 (Batches 7 and 10). No consolidation story exists for this specific pair (AUDIT-018's consolidation list does not name either page). **New finding** (duplication, not breakage).

**D9 — `sales-handoffs` edge function queries a phantom table.** Severity: **Low** (function has zero callers, so no live traffic is affected, but a future consumer would 500 immediately). `supabase/functions/sales-handoffs/index.ts` reads/writes `sales_handoffs` everywhere (`:50,77,103,132,158,180`); no migration creates a table by that name. The correct table is `sales_handoff_checklists` (`shared/sales-handoff-schema.ts:18-27`). This matches context.md's pre-existing note ("Three edge fns read tables that exist in NO schema and NO migration: sales-handoffs -> `sales_handoffs`") — **already known, restated here with the specific real-table correction.**

**D10 — No role exists for "purchasing" or "project manager" as distinct functions.** Severity: **Medium** (org-design gap, not a code bug). Grepping every role `code:` in `rbac-seeder.ts` for `PURCHAS`/`PROCURE`/`PROJECT` returns only `DIRECTOR_OPERATIONS`, `OPERATIONS_MANAGER`, `WAREHOUSE_SUPERVISOR`, `WAREHOUSE_ASSOCIATE` — no `PURCHASING_MANAGER`/`BUYER`/`PROJECT_MANAGER` role. Given the target workflow names "Purchasing & Project Management" as its own function, `operations.po.approve` currently sits only on `OPERATIONS_MANAGER` (location tier) and higher operations roles (`rbac-seeder.ts:1825-1838`), with no tier between an individual warehouse associate and a location-level operations manager. **Restates what the task prompt already flagged as known**, confirmed by direct grep.
