# Service Scope Audit — Printyx (unit installed → toner monitoring → service calls → meter billing)

Read-only. All findings verified by reading the cited file unless marked UNVERIFIED.

## 0. Architecture recap for this scope

- `service`, `service-tickets` (Express dev-only route file is `server/routes-mobile-api.ts`, edge fn exists too — **both-divergent, not proxied**), `phone-in-tickets`, `meter-reads`, `toner-replenish`, `truck-stock`, `device-monitoring`, `monitoring-clients`, `predictive-maintenance`, `predictive-dispatch`, `voice-agent`, `voice-ticket-close`, `technician-sessions`, `portal-service`, `customer-portal`, `billing`, `contracts`, `contract-tiered-rates` are all in `crmProxies` (dev forwards to the edge fn too, so dev/prod run the _same_ code for these).
- `service-tickets`, `technician-management`, `meter-readings`, `maintenance`, `mobile`, `analytics` are **both-divergent**: an Express handler and an edge fn both exist, prefix is NOT proxied, so dev and prod genuinely run different code.
- `fleet`, `parts-inventory`, `remote-monitoring`, `scheduling`, `service-contracts`, `work-orders` have **zero callers anywhere** (`docs/unreferenced-edge-fns-baseline.json`). `scheduling`→`appointments` and `technician-management`'s `/schedule` sub-route→`work_orders` read tables that exist in **no Drizzle schema and no migration**.

## 2. Workflow-stage gaps (install → toner monitoring → service call → meter billing)

**Toner/supply monitoring (ongoing, per unit)**

- Exists and is real: `printyx-client` device agent → `POST /api/client-metrics/submit` (Express, `server/routes-client-monitoring.ts:643`) → `device_metrics`/`device_registrations` (real toner levels) → `/device-monitoring`, `/supply-runway`, `/supply-orders` (all real reads/forecasts) → `/service/toner-replenish` (separate real per-machine order engine: `machine_supply_levels`/`supply_orders`).
- Missing/dead: the _second_, older toner pipeline (`auto-supply-replenishment` → `supply_monitoring`/`supply_replenishment_analytics`/`supply_usage_history`) has no writer anywhere and is permanently empty (already known, AUDIT-028/032). Two parallel systems exist for the same job; only one works. Nothing in the repo decides which one is canonical, or retires the dead one.
- Handoff gap: toner-replenish's "ship" action is a manual approval stamping a **stub** tracking number with no carrier integration — real order records exist, but nothing automatically confirms delivery or reconciles against the supplier.

**Service call — ticket creation**

- Multiple, real entry points all converge on `service_tickets`: phone-in (`phone-in-tickets` → convert), customer portal (`customer-portal` → `portal-service/classify`), predictive-failure engine (auto-creates), proactive-maintenance (manual-schedule creates a PM ticket).
- Missing UI for: direct manual ticket creation isn't exercised in the files reviewed outside `PhoneInTicketCreator` (phone-in flow) — a dispatcher wanting to open a ticket with no phone call and no portal request has no obviously-tested path in this audit (UNVERIFIED — not confirmed absent, just not found).

**Dispatch (assign technician → notify → track)**

- `/service-dispatch` is an intentional "Coming Soon" gate (AUDIT-015) — no real dispatch/routing backend exists at all.
- `ServiceHub.tsx`'s embedded "Smart Routing" modal reproduces exactly the kind of fabrication AUDIT-015 already removed from the dedicated page — invented technician names, scores, ETAs — but was never caught because the audit scoped to the standalone page, not this modal. The "Assign" button in that modal has no handler.
- Net: **there is no working assign-a-real-technician-to-a-real-ticket UI anywhere in scope.** The only real state transition into "assigned"/"in_progress" happens implicitly, via a technician checking in through `/mobile-field-service` (which is itself unusable — see below) or PATCHing the ticket directly.

**En route / on site / parts / resolved / closed (technician working the ticket)**

- The `mobile` edge fn's check-in/check-out flow is real and does move `service_tickets.status` (`open`→`in_progress`→`completed`), including geo/time/photo capture — but no reachable page can drive it against a real ticket: `/mobile-field-service` is hardcoded to a fake ticket id, `/mobile-field-operations` calls endpoints that don't exist, `/mobile-service-app`'s working parts are dev-only. The purpose-built `mobile-field` edge fn (check-in/out, log-time, parts-inventory, request-parts) has **zero callers** on any client (web, Expo, or iOS) — see AUDIT-033 and IOS-051, both open.
- **No page in this repo lets a field technician work a ticket end-to-end today** (check-in → parts used → time → photo → signature → close), despite two independently-built, working backends for exactly that job.

**Invoiced (meter billing)**

- Real, working, verified: `meter-reads` (photo submission) or manual entry → `meter_readings` → `MeterBilling.tsx` → `POST /billing/generate-invoices` → real `invoices` row, tiered-rate math. This closes the loop the prompt asked about; PROD-008a (open) is a _different_, already-dead Express duplicate of the same job and does not block this path.

## 4. Proposed stories

1. **Join equipment/technician names in the production `service-tickets` edge fn**
   As a dispatcher, I need ticket lists in production to show the equipment model and assigned technician name, not blank fields, so I can actually triage the queue.
   - `supabase/functions/service-tickets/index.ts`'s GET-list and GET-single handlers enrich each row with `equipment.model_number` and `technicians.first_name`/`last_name`, mirroring `server/routes-mobile-api.ts:62-104`.
   - Field names match what `ServiceHub.tsx` already reads (`equipmentModel`, `assignedTechnician`).
   - A new unit test (mirroring `server/tests/unit/*` patterns) asserts the edge fn response for a ticket with a real `equipment_id`/`assigned_technician_id` includes both fields.
   - `npm run check:phantom-cols` and `npm run check` stay clean.
   - Priority: 1. `dependsOn`: []

2. **Delete or gate ServiceHub's fabricated "Smart Routing" modal**
   As a dispatcher, I should not be shown invented technician names/scores/ETAs as if they were AI-generated recommendations.
   - `ServiceHub.tsx`'s `getIntelligentRoutingSuggestions` hardcoded array is removed.
   - The "Smart Routing" button either opens a `ComingSoon`-style gate (matching `AUDIT-015`'s pattern for `/service-dispatch`) or is deleted entirely until a real technician-matching backend exists.
   - No `Math.random`/hardcoded name literal remains in `client/src/pages/ServiceHub.tsx` (verifiable via `check:no-static-posture` if that guard's scope is confirmed to include this page).
   - Priority: 2. `dependsOn`: []

3. **Delete the fabricated `/api/maintenance/schedules` and `/api/maintenance/predictions` Express fixtures**
   As a service manager, the preventive-maintenance schedule list and predictions tab must show real data or an honest "not available" state, not invented customers and cost figures.
   - `server/routes-preventive-maintenance.ts`'s `GET /schedules` and `GET /predictions` handlers no longer return hardcoded arrays.
   - `PreventiveMaintenanceScheduling.tsx` and `PreventiveMaintenanceAutomation.tsx` are repointed to the real `maintenance` edge fn (once story #6 below settles the schema question) or gated with `ComingSoon` if no real backing exists yet.
   - The "Predictive Maintenance" tab in `PreventiveMaintenanceAutomation.tsx` either calls the real `predictive-failure`/`predictive-maintenance` engine or is removed as a duplicate (per the AUDIT-019 fixture-twin pattern).
   - `check:no-mocks` / `check:fabricated` pass against this file.
   - Priority: 1. `dependsOn`: [6]

4. **Make maintenance auto-generate actually persist, or delete the feature**
   As a service manager, clicking "Auto-Generate Schedules" must create real `maintenance_schedules` rows for real equipment I pick, or the button should not exist.
   - `handleAutoGenerate` in `PreventiveMaintenanceAutomation.tsx` lets the user select real equipment (from `/api/equipment` or similar), not the hardcoded `eq-001..eq-005` array.
   - The endpoint it calls performs a real bulk insert into `maintenance_schedules` (via the edge fn, per story #6) and returns the persisted rows, not an in-memory-only response.
   - The "estimated annual savings" figure is removed unless backed by a real preventive-vs-reactive cost model with cited inputs (per the CLAUDE.md rule: delete a claim with no backing data rather than fake it).
   - A test asserts a row exists in `maintenance_schedules` after calling the endpoint with real equipment ids.
   - Priority: 1. `dependsOn`: [6]

5. **Fix or gate `/mobile-field-service` so a technician can work a real ticket**
   As a field technician, I need to check in/out, take photos, and close a _real_ assigned ticket from my phone or browser, not a hardcoded demo ticket.
   - `MobileFieldService.tsx` takes a real `serviceTicketId` (route param or a ticket picker scoped to `assigned_technician_id = current user`) instead of the literal `'ticket-123'`.
   - `technicianId` is read from the authenticated session, not hardcoded `'tech-456'`.
   - The page is wired into `/service-hub`'s "Manage" action (or a comparable real entry point) so a technician reaches a specific ticket, not a static route.
   - Manual QA: log in as a seeded FIELD_TECHNICIAN, open a ticket assigned to them, check in, upload a photo, check out, and confirm `service_tickets.status` becomes `completed`.
   - Priority: 1 (Critical — this is the only page with a working check-in backend and it cannot be used at all today). `dependsOn`: []

6. **Decide and fix the schema status of `maintenance_schedules`/`maintenance_records`**
   As a platform engineer, I need to know whether these tables are real drift tables that need a Drizzle declaration and journaled migration, or dead tables that should be dropped, because right now three different sources of truth disagree (a hand-run/legacy dump has them, no migration creates them, and the edge fn reads/writes them as if they exist).
   - Run `npm run check:migrations` and confirm whether `maintenance_schedules` exists in the live DB (per COP-M07's scratch-Postgres technique) or only in `database-exports/schema.sql`.
   - If real: add a `pgTable` declaration to a `shared/*.ts` file and a journaled migration capturing the existing columns (following the `0057`/COP-M00 reconciliation pattern), so `check:phantom-cols` can see it.
   - If not real (or intentionally being replaced): decide the target table and migrate the edge fn's four `.from('maintenance_schedules')` call sites.
   - `npm run check:migrations` and `npm run check:phantom-cols` both pass afterward.
   - Priority: 2. `dependsOn`: []

7. **Retire or connect the dead `mobile-field` edge fn**
   As a mobile engineer, I have a fully-built check-in/check-out/log-time/parts-inventory backend (`supabase/functions/mobile-field/`) that literally nothing calls; either wire the canonical mobile surface to it or delete it, per the AUDIT-024 "back ends with no caller" pattern.
   - This story explicitly narrows AUDIT-033 (open) and IOS-051 (open) to just the reachability decision for `mobile-field/`, rather than re-litigating the whole three-app consolidation (CRMX-018, open, priority 4, is the bigger umbrella).
   - `npm run check:unreferenced-edge-fns` no longer lists `mobile-field` once a real caller exists, OR the directory is deleted and the baseline shrinks.
   - Priority: 2. `dependsOn`: [] (coordinate with AUDIT-033/IOS-051, do not duplicate their scope)

8. **Enforce role-scoped ticket/technician visibility in the service edge functions**
   As a FIELD_TECHNICIAN, I should see only my own assigned tickets by default; as a SERVICE_MANAGER, my team's; the tenant-wide view should require a management-level role, matching the RBAC tier model in `docs/rbac-landscape.md`.
   - `supabase/functions/service-tickets/index.ts`'s GET-list applies a server-side filter to `assigned_technician_id = current user's technician row` when the caller's role level is below the SERVICE_SUPERVISOR tier (L3), rather than relying solely on the client sending a `technicianId` query param.
   - Same treatment for `supabase/functions/technician-management/index.ts`'s technician list/detail endpoints.
   - A test using a seeded FIELD_TECHNICIAN JWT confirms `GET /service-tickets` returns only that technician's tickets.
   - `docs/rbac-landscape.md`'s edge-fn role-check count improves (currently "281 of 284 edge fns enforce auth+tenant but no role/permission check").
   - Priority: 2. `dependsOn`: []

9. **Standardize the service-ticket status/priority vocabulary**
   As an engineer, I need one enum for `service_tickets.status` and `.priority` that every writer (mobile check-in, portal classify, predictive-failure, phone-in convert, manual ServiceHub filters) actually uses, so a UI filter can never silently match zero rows.
   - Follow the pattern already established for `sales-pipeline` (COP-E02): a single source of truth served by an endpoint (e.g. `GET /service-tickets/status-vocabulary`), consumed by every status `<Select>` in scope (`ServiceHub.tsx`, `TechnicianTicketWorkflow.tsx`).
   - Write path validated with a `z.enum` derived from that same list.
   - A unit test locks the vocabulary the way `server/tests/unit/sales-pipeline-stage-vocabulary.test.ts` does for pipeline stages.
   - Priority: 3. `dependsOn`: []

10. **Consolidate the three "supply order" tables into one queryable view for ops**
    As an operations user, I want one place to see all pending toner/supply orders regardless of which pipeline created them (`supply_orders`, `device_supply_orders`, `customer_supply_orders`), instead of three disconnected admin screens.
    - Document, in one place (e.g. a header comment analogous to `billing/handlers/_context.ts`), which table each order type belongs to and why there are three.
    - Add a read-only aggregate endpoint (or extend an existing one) that unions all three for a single ops dashboard, tagged by source.
    - No existing table is merged or dropped — this is additive.
    - `npm run check:phantom-cols` and `npm run check:unreferenced-edge-fns` stay green.
    - Priority: 3. `dependsOn`: []

11. **Delete or reconnect `technician-management`'s dead `/:id/schedule` sub-route**
    As a platform engineer, a route reading a table (`work_orders`) that exists nowhere should not silently return `[]` forever; either wire it to a real schedule source (`maintenance_schedules` once story #6 lands, or `service_tickets.scheduled_date`) or remove the dead code.
    - `supabase/functions/technician-management/index.ts`'s `GET /:id/schedule` either queries a real, migrated table or is deleted along with any dead client-side type referencing it.
    - `npm run check:sql-string-tables`/`check:phantom-cols` reflect the change (removing a reference to an undeclared table either way).
    - Priority: 3. `dependsOn`: [6]

12. **Confirm and lock the meter-billing invoice path against the dead PROD-008a duplicate**
    As a billing operator, I need certainty that `MeterBilling.tsx` → `POST /billing/generate-invoices` is the one and only live contract-meter-billing path, so PROD-008a's decision (port vs. delete the unreachable Express duplicate) can close without re-verifying reachability from scratch.
    - Add `server/tests/unit/financial-convergence.test.ts` coverage (or extend the existing `KNOWN_UNREACHABLE` list per PROD-008a's own AC) confirming `MeterBilling.tsx` never calls `/api/contracts/:id/process-meter-billing`.
    - Document, in the `billing/handlers/generate-invoices.ts` header, that this is confirmed to be the frontend's only meter-billing call site (cross-reference this audit).
    - This unblocks PROD-008a's "decide whether it is still wanted" step with a definitive "no live caller" answer for this specific frontend surface.
    - Priority: 3. `dependsOn`: [] (this is a verification/documentation companion to PROD-008a, not a duplicate of it — PROD-008a itself is left untouched as the open story of record)

## Summary of what already works well (don't re-litigate)

- Device → toner monitoring: `printyx-client` agent → Express `client-metrics`/`client-monitoring` routes → real `device_metrics`/`device_registrations` → `/device-monitoring`, `/supply-runway`, `/supply-orders`, `/service/toner-replenish` is a genuinely solid, real pipeline.
- Customer portal → service ticket: verified end-to-end, lands in the real tenant ticket queue.
- Meter reading → billing: verified end-to-end, real tiered-rate invoice generation.
- Predictive-failure and proactive-maintenance both create real `service_tickets` rows — the "real" predictive engine is not the fabricated one under `/preventive-maintenance-automation`.
- `/service-dispatch`'s prior fabrication was already caught and gated (AUDIT-015) — a good template for what should happen to ServiceHub's Smart Routing modal (proposed story #2) and the maintenance fixtures (proposed stories #3-4).
