# Audit F — Role tiers and data scoping (Printyx)

Read-only audit. All claims verified from the repository at `/home/user/Printyx`; anything not directly verified is marked UNVERIFIED. `docs/rbac-landscape.md` (SEC-EDGE-002) already establishes the "two role systems" landscape — this audit builds on it and does not re-derive what it already proved. New material here: (1) whether the JWT-claim mechanism either system depends on is ever populated, (2) whether the nine core list endpoints the owner cares about apply any scoping beyond `tenant_id`, (3) that the one purpose-built scoping engine (`HierarchicalQueryBuilder`, and its RBAC-008 successor `scope-middleware.ts`) is dead code with zero callers, (4) that two prd.json stories (RBAC-008, RBAC-009) are marked `passes: true` while verifiably not implementing what they claim, and (5) that the org hierarchy (locations/regions/teams/manager_id) has no reachable UI to populate it.

**Bottom line**: tenant isolation holds everywhere checked. Intra-tenant role-based _data_ scoping (L1-2 own / L3-4 team-location / L5-6 region / L7-8 company) does not exist anywhere on a live code path — not client-enforced-only, not server-enforced-badly, but **absent**. Every authenticated member of a tenant who calls a core list endpoint gets every record in the tenant, regardless of role. The only enforcement that exists is client-side sidebar/route hiding, which a direct API call bypasses trivially, and even that is undermined by the JWT never carrying the role-level claim it depends on.

## 4. Supporting findings

**(a) Effective role in production**: `useSupabaseAuth.ts` calls `getApiUrl('me')` → `GET /api/me`, served by `supabase/functions/me/index.ts`. It joins `users.role_id → roles` (System A) and returns `{level, permissions, canAccessAllTenants}` — no `code`, no `enhancedPermissions`, no `locationId`/`regionId`/`teamId`. `app_metadata` carries `tenantId`, `roleId`, `accessScope`, `isPlatformUser` only (verified in §1) — no `level`, no `permissions`, no location/region.

**(b)** See §2 table.

**(c) Location/region/territory data model**: `locations` (`shared/schema.ts:895`), `regions` (`:923`), `teams` (`:947`) exist, and `users` carries `primaryLocationId`, `regionId`, `teamId`, `managerId`, `accessScope` (`:1006-1013`). **No UI populates any of it.** `docs/unreferenced-edge-fns-baseline.json` lists `locations`, `regions`(implicitly via `territories`/`sales-territories`), `teams`, `role-management`, `roles`, `user-management`, `users-team`, `user-assignments`, `rep-capacity` — all 0-caller edge functions (`:56,68-85`). Grepping every client tree (`client/src`) for `/api/locations` or `/api/regions` found no caller. The one "territories" UI that exists, `PlatformTerritories.tsx`, calls `/api/platform-crm/territories` — Printyx's own platform-level customer-territory CRM, unrelated to tenant org structure. `salesTeams`/`salesTeamMembers` (a separate, newer team model at `shared/schema.ts:3502-3620`) is referenced only by the unmounted `routes-crm-goals.ts` and two seed scripts with no npm entry point. **Conclusion: `primaryLocationId`/`regionId`/`teamId`/`managerId` are effectively always null in any real tenant**, so even a correctly-wired scoping engine would have nothing to filter on.

**(d) Sidebar per seeded role, and what actually happens**: `usePermissions.ts` reads `user.role.enhancedPermissions` (System B) first, falling back to `user.role.permissions` (System A JSONB) expanded via `expandLegacyPermissions`. Since `/api/me` (production) never returns `enhancedPermissions` (finding (a)), production **always** takes the legacy-expansion branch. A SALES_REP's System A role row would need `permissions: {sales: true}` (or similar) for the sidebar to show CRM at all — and per §5(e) below, System A's `roles` table has **no seed path** that would ever create a SALES_REP row in the first place. So the honest answer to "does a SALES_REP see Billing Hub / Reports / Administration" is: **there is no SALES_REP role for it to be tested against in a real, non-manually-bootstrapped tenant** — `role-seeder.ts`, the only file that defines a `SALES_REP` row with a `code` field matching System A's shape, has zero importers and no npm script (confirmed by grep across the whole tree excluding the files themselves). If a role _were_ manually inserted with `permissions: {billing: false, reports: false, system: false}`, `expandLegacyPermissions` would correctly withhold `finance.*`/`reporting.*`/`admin.*` codes and the sidebar would hide those sections — the vocabulary itself is sound; only its data source in production is empty.

**(e) Role Management UI**: `RoleManagement.tsx` (routed at `/access-control`, `App.tsx:1058`) calls `/api/rbac/*`, served by `supabase/functions/rbac/index.ts` (the `rbac` prefix is "both-divergent" — not proxied — so production genuinely runs this edge fn). Its `GET /rbac/status` gates the whole page: it counts `enhanced_roles` rows for the tenant and shows an "initialize RBAC" prompt if zero — true for essentially every tenant per rbac-landscape.md. The page's own "initialize" action calls `POST /api/rbac/seed`, which **returns 501** in production: `{error: 'RBAC seeding is not available on the edge function yet', code: 'RBAC_SEED_NOT_PORTED'}` (`rbac/index.ts:300-312`), and this exact gap is tracked open as prd.json `EDGE-002h`. There is also no `POST /rbac/roles` (create-role) endpoint at all — only `assign-role` (assign an _existing_ role, gated by `currentLevel < 5 → 403`, itself dependent on `roles.level` which requires the never-seeded System A catalogue) and the dead-end `seed`. **A COMPANY_ADMIN cannot create a new role or initialize the role catalogue for their tenant in production today**, by any UI path found.

## 5. Defects found

### D1 — CRITICAL. Zero server-side, role-tiered data scoping on any live endpoint; the purpose-built engines are both dead code

Every core list endpoint (`business-records`, `deals`, `service`, `tasks`, `invoices`, `meter-reads`, `purchase-orders`, `equipment`) filters by `tenant_id` only. The two implementations that would fix this — `HierarchicalQueryBuilder` (`server/middleware/hierarchical-query-builder.ts`) and `scope-middleware.ts`'s `applyScopeFilter()` — have **zero live callers** each, confirmed by grep and both listed in `docs/server-orphans-baseline.json:40,132,139`.
**Severity**: Critical (data isolation, not just UX — a SALES_REP sees every other rep's pipeline, commissions data attached to deals, every technician's service history).
**prd.json coverage**: `RBAC-008` ("Implement role-scoped API data filtering so reps only see their own records") is the exact story for this gap. **It is marked `passes: true`.** Its own `notes` field says otherwise verbatim: _"hierarchical-query-builder.ts exists... but is not applied consistently across all list endpoints. Currently most endpoints only filter by tenantId... This is a data security story, not just UI."_ None of its 10 acceptance criteria are met: `buildScopedQuery()` (AC1) doesn't exist anywhere in the tree (`grep -rn buildScopedQuery` finds only an unrelated same-named local function in `sales-rep-assignments/index.ts:558`); `scope-middleware.ts` (AC5) was created but has no importers; no integration test named "rep A/rep B" scope isolation (AC7) exists in `server/tests/integration/`. **This is the single highest-value action item: reopen RBAC-008, correct the `passes` flag, and redirect the fix to the edge-function layer** (the Express-only `scope-middleware.ts` cannot run in production regardless of wiring, since production serves these prefixes from edge functions, not Express).

### D2 — CRITICAL. JWT never carries `roleLevel`/`role`/`permissions`; the only two working level-checks (Express + edge) both silently default every user to level 1

Confirmed no code path ever writes these claims via `admin.createUser`/`admin.updateUserById` (2 total `updateUserById` calls in the repo, neither touching `app_metadata`). `mobile-auth`'s enrichment only decorates the JSON response body, not the signed token. Effect: `_shared/rbac.ts`'s `getRoleLevel()` and `supabase-auth.ts`'s JWT parsing both return the `?? 1` default for every user including real platform admins, on every one of the 5 edge functions and ~20 Express route files that consult it.
**Severity**: Critical for the 5 edge fns that gate on level (`erp-integration`, `monitoring-clients`, `device-monitoring`, `blog-agents`, `dashboard-widgets`) — they either lock out everyone or (via `isPlatformAdmin` flag path, also never set) never grant elevated access to anyone.
**prd.json coverage**: Not found under this framing. `SEC-EDGE-002` (open) covers the adjacent "two vocabularies" problem but does not identify that the JWT claim itself is never populated by any issuance path. **New finding — no covering story.**

### D3 — HIGH. Role-based dashboard widget layouts never resolve to a role-specific layout for any real (non-platform-admin) tenant user

`RoleBasedDashboard.tsx:26-55`'s `effectiveRoleCode` resolution: `if (roleCode) return roleCode.toUpperCase();` fires unconditionally, because `usePermissions.ts`'s `roleCode` (`role?.code || role?.name || 'USER'`) is **never falsy** — `/api/me` never returns `role.code` (confirmed, zero occurrences of `code` in `me/index.ts`), so `roleCode` resolves to `role.name` (a human string like `"Company Administrator"`) or the literal `'USER'`. `.toUpperCase()` on `"Company Administrator"` yields `"COMPANY ADMINISTRATOR"` (with a space), which matches no key in `DEFAULT_ROLE_LAYOUTS` (keys are `COMPANY_ADMIN`, etc. — underscored). The entire smarter fallback beneath it (lines 30-54, which infers a sensible code from `level`/`department` when `role.code` is missing) is **unreachable dead code**, because the branch above it always returns first. Net effect: `getDefaultLayout()` misses for every real user and returns `DEFAULT_ROLE_LAYOUTS['DEFAULT']` regardless of role, except the one hard-coded `isPlatformUser → 'PLATFORM_ADMIN'` shortcut at line 27 (itself gated on a flag that's never true per D2).
**Severity**: High (feature completely inert, not partially degraded).
**prd.json coverage**: `RBAC-009` ("Add role-specific dashboard views that surface relevant KPIs and actions per role") is marked `passes: true` and describes exactly this feature (L1-2/L3-4/L5-6/L7-8 tiered widget tiers). Its notes claim _"The API scoping from RBAC-003 means the data returned is already role-scoped"_ — RBAC-003 is a permission-gating story (403 on unauthorized actions), unrelated to data scoping, and is itself a separate, narrower concern from D1. **RBAC-009's `passes: true` is false**, on the same evidentiary basis as D1.

### D4 — HIGH. System A `roles` table (the table production signup, `/api/me`, and the `rbac` edge fn all depend on) has no seed path that will ever run

The only file that creates a `COMPANY_ADMIN`-shaped row matching System A's schema (`id, name, code, level, permissions` JSONB) is `server/role-seeder.ts`. It has zero importers and no `package.json` script (confirmed: `grep -rn "role-seeder"` across the whole tree, excluding the file itself and docs, returns nothing). `multi-location-role-seeder.ts` and `initialize-roles.ts` are equally unreachable. `signup/index.ts` only **looks up** `code = 'COMPANY_ADMIN'`; it never creates the row, and fails loudly (`MISSING_ADMIN_ROLE`) if absent.
**Severity**: High — this is a prerequisite for literally any role hierarchy to exist per tenant; without a manual, out-of-band DB insert, self-service signup itself is broken.
**prd.json coverage**: Already fully documented as the centerpiece of `SEC-EDGE-002` (open) and `docs/rbac-landscape.md`. **Not new** — cited here only because it's the root cause underneath D3/D5's "which role does a user actually have" question.

### D5 — MEDIUM. `/api/me` fails open: a user with no resolvable role gets every module permission

`supabase/functions/me/index.ts:130-138` — when `roleId` is unset or the `roles` row lookup misses, the function returns `role: {level: 1, permissions: allModulePermissions(), ...}` (every module boolean `true`) rather than a restricted default. `expandLegacyPermissions(allTrue, level=1)` grants the full L1 tier of every module (sales, service, inventory, finance level-1 codes, reports, `system` module requires `level>=3` so admin codes are still gated by level, but every other module's L1 codes are granted). A brand-new user whose `role_id` hasn't been set yet (the normal state before an admin assigns one, given D4/D6) gets meaningfully more access than intended by default.
**Severity**: Medium (bounded by level gating on the admin module, but real for sales/service/finance/reports at their L1 tier).
**prd.json coverage**: Not found under this framing. **New finding.**

### D6 — HIGH. No reachable UI exists to create additional roles, invite/assign users to a role, or populate location/region/team/manager

`RoleManagement.tsx`'s only mutating action (`POST /rbac/seed`) returns 501 in production (tracked as `EDGE-002h`, open); no `POST /rbac/roles` create-role endpoint exists; `roles`, `role-management`, `user-management`, `users-team`, `user-assignments`, `locations`, `territories`, `sales-territories`, `rep-capacity`, `teams` edge functions are all confirmed zero-caller (`docs/unreferenced-edge-fns-baseline.json:56,68-85`). No `/api/users` POST (create-user) call was found in any `.tsx` page. Even if the JWT-claim and query-scoping defects above were fixed today, there is no path by which a COMPANY_ADMIN populates the org structure (which reps report to which manager, which location/region each user belongs to) that any scoping engine would need to filter on.
**Severity**: High — this is the reason D1's fix can't just be "wire up `scope-middleware.ts`"; the columns it would filter on are unpopulated by construction.
**prd.json coverage**: Adjacent to `EDGE-002h` (the seed-endpoint gap) but the missing invite/assign/org-structure UI as a whole is **not covered** by any open story found by keyword search (`user-management`, `role-management`, `invite`, `assign role`, `locations`, `regions` against `userStories`).

### D7 — MEDIUM. No role codes exist anywhere in the seed catalogues for Purchasing, Project Management, Delivery/Install, or Network Setup

Confirmed by grepping every `code: '...'` literal in `rbac-seeder.ts` (131 codes) and the role lists in `role-seeder.ts`/`multi-location-role-seeder.ts` for `PURCHAS|PROJECT|DELIVER|INSTALL|NETWORK` — the only hit anywhere is a _permission_ code, `service.equipment.install`, not a role. The owner's target workflow (`...handoff to Purchasing & Project Management -> Logistics (receiving, building/configuring, mechanical + network functional check) -> Delivery -> Acceptance...`) names four job functions with no corresponding role in any seeder, at any level.
**Severity**: Medium (a gap to fill, not a live defect).
**prd.json coverage**: Not found by keyword search. **New finding.**
